# Персональный Windows-агент

Первый этап проекта: Telegram → ограниченный контекст → Brain → локальная память; Windows-наблюдение работает отдельно и не обращается к LLM. Требования сохранены в [docs/requirements.ru.md](docs/requirements.ru.md), состояние — в [docs/status.md](docs/status.md).

По явному запросу пользователя в локальном `config.local.toml` включён `pc_access = "full"`: PRIMARY может читать локальные диски, записывать UTF-8 файлы, выполнять PowerShell и запускать программы от имени текущего пользователя Windows, получать скриншоты. SECONDARY получает чтение. В примере конфигурации по умолчанию `pc_access = "read"`; переключение прав происходит только через локальную настройку. Модель имеет собственные инструкции и вызывает инструменты через сервис, а не через инструменты Codex. Повышения системных прав и автозапуска нет.

## Быстрая проверка без Telegram

Python 3.12+ и PowerShell, из папки проекта:

```powershell
py -m venv .venv
py -m pip install "uv==0.13.5"
py -m uv sync --locked --group test
.\.venv\Scripts\python.exe -m pytest -v
.\.venv\Scripts\python.exe -m personal_agent doctor --config config.example.toml
.\.venv\Scripts\python.exe -m personal_agent demo
```

`doctor` не подключается к сети. `demo` использует синтетические события и явно помеченный MockBackend. Это проверка интеграции, а не настоящий ответ GPT. В проекте уже создано отдельное окружение `.venv`.

## Настройка Telegram позднее

Локальный бот уже настроен в игнорируемом Git файле `config.local.toml`. Для повторного запуска в фоне:

```powershell
.\Start-PersonalAgent.cmd
```

`Start-PersonalAgent.cmd` запускает PowerShell с политикой `Bypass` только для этого процесса, поэтому не требует менять системную ExecutionPolicy. При желании можно вызвать `.\Start-PersonalAgent.ps1` из уже разрешающей политики. На рабочем столе создан ярлык `Personal Agent.lnk`, который запускает этот `.cmd`. Скрипт читает токен из `C:\Users\nagas\Desktop\bot_api.txt`, передаёт его только через окружение процесса и запускает daemon со скрытым окном. Повторный запуск при действующем PID не создаёт второй экземпляр. Логи и сведения о процессе — в `.state/logs/` и `.state/daemon-process.json`. Этот запуск не регистрирует автозапуск Windows. После перезагрузки скрипт нужно выполнить снова. Настроены project roots этого проекта и существующего NTM-порта. Изменения файлов поступают через Windows file events; очередь ограничена 10 000 путями, число отброшенных событий видно в `observer_health`.

Инструкция ниже подходит для ручной настройки другого бота или переноса проекта.

Токен хранится только в переменной окружения. Не вставляйте его в исходники и не отправляйте в чат. Можно скрыто ввести токен в текущем PowerShell:

```powershell
$botSecret = Read-Host 'Токен Telegram-бота' -AsSecureString
$env:TELEGRAM_BOT_TOKEN = [System.Net.NetworkCredential]::new('', $botSecret).Password
```

Чтобы получить ID, напишите боту с каждого из двух аккаунтов любое сообщение, затем явно запустите:

```powershell
.\.venv\Scripts\python.exe -m personal_agent telegram-ids
```

Команда обращается к Telegram, показывает только числовые ID отправителей личных сообщений, ничего им не отвечает и не запускает daemon. Не запускайте её одновременно с другим poller этого бота. Если список пуст, напишите боту и повторите команду.

```powershell
Copy-Item config.example.toml config.local.toml
# В config.local.toml замените primary_id и secondary_id на разные реальные ID.
# Добавьте известные project_roots. Выберите проверенный backend по backend-spike.md.
.\.venv\Scripts\python.exe -m personal_agent run --config config.local.toml
```

По умолчанию используется `codex_subscription`: официальный Codex с существующей авторизацией ChatGPT. Этот backend проверен реальным ответом `PONG` с отключёнными инструментами. Команды `doctor` и `demo` остаются офлайн; для отдельного тестового daemon можно явно выбрать `mock`. Экспериментальный web backend включается только при `backend = "codex_chatgpt_web"` и `web_enabled = true`; он использует Codex CLI как transport к loopback bridge. Его base URL задайте по установленному bridge, не полагайтесь на пример порта. API key OpenAI не требуется. Существующие настройки Codex и bridge не меняются.

Проверенные версии Codex: встроенная `0.165.0-alpha.1.2` плюс версии из `<data_dir>/verified_codex_versions.json`. Неизвестную версию backend перед первым запросом проверяет локальным wire self-check без обращения к модели: Codex направляется на локальную заглушку и должен прийти на наш gateway с Bearer-авторизацией, отправить ровно один запрос с нашей persona, нашим промптом и только предложенными функциями, разобрать синтетический финальный SSE и не обращаться к чужим хостам (служебные соединения Codex с chatgpt.com перехватываются локальной заглушкой и не считаются нарушением). При успехе версия записывается в файл и принимается, иначе запрос отклоняется с `unverified_codex_version` и подробностью. Результат проверки кэшируется на процесс, ответы `--version` и `login status` — на 10 минут. Ручной запуск: `.\.venv\Scripts\python.exe scripts\verify_codex_wire_check.py`.

У Telegram-агента собственные инструкции и контекст. Локальная граница запроса заново собирает только persona Personal Agent, его пакет данных и явно приложенные изображения; глобальный `AGENTS.md`, память/skills и служебные сообщения Codex до модели не доходят. Подписка используется для авторизации. Старая история остаётся в SQLite, но ответы до обновления не подмешиваются в новый контекст. Проверка: `.\.venv\Scripts\python.exe scripts\verify_backend_isolation.py`; подробности — в `docs/backend-isolation.md`. Пакет контекста — до 80 000 символов: профиль, предпочтения, до 30 последних реплик (по 2000 символов), каталоги недавних картинок и документов, неотвеченные сообщения и сводка активности за два часа; при нехватке места сначала отбрасывается релевантная память, затем сокращается сводка активности, затем самые старые реплики. Persona (около 2,6 тыс. символов) и описание полей контекста написаны один раз и не повторяют друг друга.

Третий ID и сообщения из групп игнорируются. PRIMARY и SECONDARY получают чат и чтение общей памяти. История диалогов выбирается по ID. SECONDARY не может менять настройки и останавливать daemon. `/help` показывает команды, `/status` — расход за день UTC. Во время ответа можно отправить новую инструкцию: предыдущий ответ этого аккаунта отменяется, контекст собирается заново.

Обычный диалог, `/start`, `/model`, `/instructions`, `/capabilities`, `/memory` и `/help` отвечают через модель. Сервис передаёт реальные настройки, путь памяти и результаты чтения; готовых разговорных ответов и подмены составного вопроса шаблоном нет. Только точные `/status` и `/diagnostics` формируют отчёты по текущим данным без LLM. На обычные вопросы о состоянии сервиса и расходе модель сама выбирает read-only `service_diagnostics` и получает свежую безопасную выжимку проверки backend, счётчиков UTC и сохранённых записей observer/Telegram; точные слова для маршрутизации не требуются. Сохранённые признаки здоровья могут быть устаревшими, а успешная проверка backend не подтверждает доставку сообщений. Пожелания вроде «отвечай проще, не так строго» сохраняются по аккаунту и восстанавливаются из его истории.

Модель работает с инструментами через нативные вызовы функций Responses API: каждый ход — один запрос к модели, внутри которого локальный gateway выполняет цикл «вызов функции → результат → продолжение» (до 8 раундов и 24 вызовов за ход; изображения из инструментов возвращаются модели как картинки). Функции предлагаются в каждом сообщении, включая продолжения «давай» и произвольные формулировки; текстовых JSON-протоколов и разбора фраз нет, выбор по смыслу делает модель. Набор: `list_directory`, `find_files`, `read_file`, `read_active_window`, `take_screenshot`, `read_browser_page`, `view_recent_media`, `watch_video`, `read_attachment`, `web_search`, `web_open`, `search_memory`, `activity_timeline`, `save_preferences`, `save_profile`, `service_diagnostics`; `write_file` и `run_command` предлагаются только PRIMARY при `pc_access = "full"` и проходят ActionBroker и ActionGate. Если после вызовов инструментов модель вернула пустой ответ, сервис один раз повторяет запрос без инструментов с записанными результатами. Пока ход идёт, бот показывает «печатает…» (`sendChatAction` каждые ~4,5 с).

`.\.venv\Scripts\python.exe scripts\verify_conversation.py` проверяет настоящую модель на временных файлах: чтение, запись, PowerShell, восстановление после прежнего отказа, повторное прикладывание синтетической картинки. Использует подписку; частный экран и сеть Telegram не задействует. Флаг `--desktop-only` отдельно проверяет исходную проблемную фразу и перечисление настоящего рабочего стола моделью; в консоль выводятся только счётчики.

Доступны также команды наблюдения:

```text
/ls C:\Users\nagas\Desktop
/read C:\проект\README.md
/screenshot
```

Точные команды `/ls`, `/read`, `/screenshot` выполняются сервисом до модели; всё остальное модель решает сама через нативные функции. `list_directory` читает до 100 записей. `read_file` и `read_attachment` читают текст кусками по 32 KB (до 64 KB) из UTF-8, UTF-16 (по BOM) и Windows-1251 и возвращают `offset`, `next_offset`, `total_bytes`, `eof`, `encoding`; чтобы прочитать длинный файл целиком, модель продолжает с `next_offset`. `find_files` ищет по имени (glob или слово) рекурсивно: глубина 8, до 20 000 записей, 8 секунд, без ссылок/junction и служебных каталогов с учётными данными. Известные файлы авторизации, приватные ключи и сетевые/device paths отсекаются на каждом куске. `web_open` принимает `result_id` поиска или публичный `http(s)` URL: до трёх редиректов вручную, каждый переход заново проверяется (схема, порт, только публичные IP), поддерживаются HTML и `text/plain`; за ход не более 4 поисков и 4 открытий. В полном режиме PowerShell работает с правами пользователя Windows и способен выполнять произвольные команды; фильтр специализированного чтения не является sandbox для PowerShell. Вывод команд ограничен 16 KB и очищается от распознаваемых токенов/ключей, запись через `write_file` — 256 KB. Команды имеют timeout до 120 секунд; отмена останавливает собственный процесс команды. Дочерней команде не передаются токен бота и API auth env. Содержимое файлов и результатов инструментов передаётся как данные.

Захват и отправка скриншота разделены. Модель выбирает чтение текста активного окна или снимок по смыслу текущего запроса. Снимок по умолчанию используется только для анализа; если пользователь просит показать или прислать изображение в Telegram, модель вызывает `take_screenshot` с `send_to_user`. Следующий вопрос о скриншоте повторно использует файл через `view_recent_media`. Native Codex tools остаются выключены; PowerShell выполняет отдельный host executor при разрешённом полном доступе. Для Web backend анализ изображения пока недоступен. Защищённые/заблокированные Windows-окна могут быть неполными; GDI-захват ограничен 16 мегапикселями. Фонового потока снимков нет.

Просмотр видео работает через инструмент `watch_video` и модуль `personal_agent.video`. Общедоступные ссылки (YouTube, TikTok и др.) скачиваются через `yt-dlp` в изолированном дочернем процессе без доступа к кукам браузера. Видео из Telegram (`video`, `video_note`, `animation`, видео-документы) принимаются через `AttachmentPipeline` в пределах `max_attachment_bytes`. Ролик нарезается на раскадровки (contact sheets по сетке до 8 плиток с метками времени) и снабжается субтитрами или речью (локальный Whisper). В последующих репликах («а что в конце?») модель вызывает `watch_video(media_id=..., start_seconds=...)` для повторного просмотра нужного фрагмента. Скачанные видео хранятся 7 дней и удаляются автоматически. Если ролик не помещается в лимит даже в самом низком качестве, остаются метаданные, субтитры и постер без кадров; об этом явно сообщается.

`/diagnostics` проверяет состояние daemon, observer, polling, backend и последние ошибки. Код ошибки и безопасное описание сохраняются; сырые provider stderr, токены и HTTP URL в чат не выводятся. Причину исторического сбоя 26.10 в 11:55 восстановить невозможно: старая версия сохраняла только `RuntimeError`.

PRIMARY может отправить точную фразу `АВАРИЙНОЕ ВЫКЛЮЧЕНИЕ` с пробелами по краям. Она обрабатывается до LLM. Обычная остановка — Ctrl+C. В полном режиме PRIMARY может поручать управление приложениями через PowerShell. При служебной отмене daemon завершает собственные процессы транспорта, STT и текущей команды. Автозапуск не регистрируется.

## Память и наблюдение

В `data_dir` создаются `memory/state.sqlite3`, `current/context.md`, `days/`, `projects/`, `attachments/`, `transcripts/` и служебные каталоги. SQLite содержит канонические события, provenance, сообщения, offset polling и метрики. Markdown — представления с IDs свидетельств; их можно восстановить из базы. FTS5 ищет без vector DB. Скриншоты удаляются через 7 дней; сырые события Windows/filesystem/vision/PowerShell — через 30 дней. История сообщений и постоянный профиль пользователя сохраняются отдельно.

Windows-датчик читает foreground window, PID/exe/title, процессы и idle time. Изменения файлов в настроенных проектах поступают через watchdog/ReadDirectoryChangesW; содержимое пассивно не читается и не меняется. Это best-effort наблюдение: оно не обнаруживает все открытые файлы, все кратковременные процессы и точный смысл работы. Низкая уверенность явно отражается в контексте. Нет фоновых screenshots, чтения буфера обмена, keylogging, браузерного управления, Discord capture или фоновых облачных вызовов.

При визуальном запросе агент сам выбирает доступные инструменты наблюдения. Скриншот отправляется в Telegram только если модель распознаёт явную просьбу пользователя; анализ сам по себе не прикрепляет изображение. Расширение [browser-companion](browser-companion/README.md) дополнительно передаёт текущую страницу Chrome/Edge без скриншота; его нужно загрузить в браузер и связать с локальным приёмником.

Вложения сохраняются под случайными локальными именами; оригинальное имя — только метаданные. Текстовые документы индексируются в пределах 32 KB; Telegram-фотографии, документы с PNG/JPEG/GIF/WEBP и статические WEBP-стикеры передаются в vision при поддержке backend. Формат проверяется по байтам, а не имени файла; изображения ограничены 10 MB и локальным лимитом вложений. Анимированные TGS/WEBM-стикеры локально преобразуются в последовательность до четырёх PNG-кадров с отметками времени; модель получает кадры по порядку и может описать движение. Для TGS установлен rlottie-python, для WEBM используется FFmpeg из imageio-ffmpeg (или явно заданный ffmpeg_executable). При обработке нет скачивания дополнительных программ или отправки стикера стороннему сервису; в настроенную модель уходят только подготовленные кадры. Повреждённые файлы и превышение лимитов дают явный статус. Голосовые можно распознавать локальным `whisper.cpp`: укажите пути к `whisper_executable` и `whisper_model`; FFmpeg берётся из `imageio-ffmpeg`, если `ffmpeg_executable` не задан. Модель и Whisper устанавливаются отдельно. Автоматических загрузок и облачного STT нет. Без настройки голосовое сохраняется с явным сообщением, что расшифровка недоступна.

Исходный звук и транскрипции остаются локально. В Brain попадает только ограниченный пакет для явного пользовательского запроса; его передача выбранному backend является частью чата. Оценки токенов приблизительные (`число символов / 4`), это не данные биллинга.

## Источники интерфейсов

- [Telegram Bot API](https://core.telegram.org/bots/api): long polling, private sender IDs, загрузка файлов.
- [OpenAI Codex non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode): официальный CLI transport.
- [HTTPX async](https://www.python-httpx.org/async/): отменяемые HTTP-запросы.
- [whisper.cpp](https://github.com/ggml-org/whisper.cpp): локальная CLI-расшифровка. Реальная точность STT требует проверки с установленной моделью.

Design notes и точные результаты backend/Windows-проверок находятся в `docs/`. Живая Telegram-сессия и распознавание настоящего аудио не считаются проверенными по результатам mock-тестов.

## Предпочтения и доставка

Пожелания «пиши без Markdown», «не форматируй ответы», «говори проще», «скриншоты присылай только по прямой просьбе» и «найди имя на стикере без вопросов» сохраняются отдельно для каждого Telegram ID в SQLite и переживают перезапуск. Для plain text форматирование убирается также перед отправкой; содержимое кода и адреса ссылок сохраняются. Подтверждение сохранения строится на фактическом результате записи, а не обещании модели. Обновления из файлов, изображений или цитат предпочтения не меняют.

Постоянный профиль записывается или расширяется только по явной просьбе, отдельно для Telegram ID отправителя, с проверкой чтением после записи. Он передаёт модели личные факты и предпочтения; права и правила сервиса от него не меняются. Поиск памяти исключает события с данными другого отправителя.

Текстовое вложение без подписи автоматически передаётся модели для чтения. Команда сохранения профиля работает и до отправки файла, и после неё; «следующий файл» ожидает новое вложение. Для профиля читается полный сохранённый UTF-8 файл, а не обрезанный разговорный preview. Предел профиля — 24 000 символов; ошибки чтения и превышение размера возвращаются явно, без частичной записи.

Реальные проверки диалога используют только `gpt-6-luna`, reasoning `medium`; рабочая модель из `config.local.toml` для них не наследуется. `scripts/verify_interaction.py` проверяет предпочтения и изображения, `scripts/verify_interaction.py --profile-only` — чтение файла, сохранение профиля и память после перезапуска, `scripts/verify_interaction.py --tool-choice-only` — выбор моделью чтения и разрешённой записи по непрямой формулировке, а `scripts/verify_interaction.py --visual-tool-choice-only` — визуальный выбор и отправку только синтетического изображения через локальную заглушку Telegram. Проверки используют временные данные; живой экран и Telegram не затрагиваются.

Вынесены отдельные `preferences.py`, `attachments.py` и `delivery.py`; цикл инструментов и полный доступ PRIMARY сохранены. Скриншоты и сырые наблюдения очищаются по срокам хранения; большой рефакторинг остальных подсистем в это обновление не входит.

Анимации ограничены 10 MB исходного файла, 2 MB распакованного TGS JSON, 10 секундами и четырьмя кадрами не более 512×512. Декодирование выполняется в отдельном скрытом процессе с ограничением времени; отмена запроса останавливает обработку. Повторный вопрос о стикере использует сохранённую последовательность своего аккаунта. Набор кадров — выборка анимации, а не непрерывный видеовход. Реализация использует [rlottie-python](https://pypi.org/project/rlottie-python/) и [imageio-ffmpeg](https://github.com/imageio/imageio-ffmpeg).
